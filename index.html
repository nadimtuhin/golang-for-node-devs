Go Fiber Handler + Validator (internal/handlers/products.go)
package handlers

import (
	"context"
	"time"

	"example.com/tomdoestech/internal/db"
	"github.com/go-playground/validator/v10"
	"github.com/gofiber/fiber/v2"
	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/bson/primitive"
)

type Product struct {
	ID        primitive.ObjectID `json:"_id" bson:"_id" validate:"required"`
	CreatedAt time.Time          `json:"createdAt" bson:"created_at" validate:"required"`
	UpdatedAt time.Time          `json:"updatedAt" bson:"updated_at" validate:"required"`
	Title     string             `json:"title" bson:"title" validate:"required,min=12"`
}

type ErrorResponse struct {
	FailedField string
	Tag         string
	Value       string
}

func ValidateProductStruct(p Product) []*ErrorResponse {
	var errors []*ErrorResponse
	validate := validator.New()
	err := validate.Struct(p)

	if err != nil {
		for _, err := range err.(validator.ValidationErrors) {
			var element ErrorResponse
			element.FailedField = err.StructNamespace()
			element.Tag = err.Tag()
			element.Value = err.Param()
			errors = append(errors, &element)

		}
	}
	return errors
}

func CreateProduct(c *fiber.Ctx) error {
	product := Product{
		ID:        primitive.NewObjectID(),
		CreatedAt: time.Now(),
		UpdatedAt: time.Now(),
	}

	if err := c.BodyParser(&product); err != nil {
		return err
	}

	// Could also be broken down to be
	// err := c.BodyParser(&product)

	// if err != nil {
	// 	return err
	// }

	errors := ValidateProductStruct(product)

	if errors != nil {
		return c.JSON(errors)
	}

	client, err := db.GetMongoClient()

	if err != nil {
		return err
	}

	collection := client.Database(db.Database).Collection(string(db.ProductsCollection))

	_, err = collection.InsertOne(context.TODO(), product)

	if err != nil {
		return err
	}

	return c.JSON(product)

}

func GetAllProducts(c *fiber.Ctx) error {
	client, err := db.GetMongoClient()

	var products []*Product

	if err != nil {
		return err
	}

	collection := client.Database(db.Database).Collection(string(db.ProductsCollection))

	cur, err := collection.Find(context.TODO(), bson.D{
		primitive.E{},
	})

	if err != nil {
		return err
	}

	for cur.Next(context.TODO()) {
		var p Product
		err := cur.Decode(&p)

		if err != nil {
			return err
		}

		products = append(products, &p)

	}

	return c.JSON(products)

}

📦 Dependency Management: Go Modules vs npm

How go.mod and go.sum replace package.json, package-lock.json, and the node_modules folder.

📄 1. package.json vs go.mod

In Node, package.json lists package names and semantic version ranges registered on npmjs.org.

In Go, there is NO centralized npm registry. go.mod declares dependencies using direct Git repository paths (e.g., github.com/gofiber/fiber/v2).

🔒 2. package-lock.json vs go.sum (Cryptographic Security)

go.sum is a cryptographic SHA-256 ledger. If a package author deletes their repo or force-pushes a malicious change to a Git tag (supply chain attack), the Go compiler detects the mismatch and aborts the build.

🗑️ 3. Where is node_modules?

Go never creates a local dependency folder in your project. Dependencies are downloaded once globally to $GOPATH/pkg/mod/ and shared across all projects.

🧠 The Go Philosophy & The Zen of Go

A guide for Node.js developers transitioning from dynamic, metaprogramming-rich JavaScript to Go’s radical simplicity, explicit typing, and performance-first ergonomics.

💡 1. "Clear is better than clever."

In Node.js: Clever tricks abound: monkey-patching prototypes, Proxy interceptors, magic reflection, complex decorators, and nested higher-order one-liners.

In Go: Boring code is praised. A junior developer should be able to read a senior engineer's code in 10 minutes. If code looks clever, it is refactored into simple, linear statements.

📦 2. "A little copying is better than a little dependency."

In Node.js: Projects import micro-packages for trivial tasks (e.g., left-pad, is-odd). Result: 1,500 sub-dependencies, bloated node_modules, and supply-chain vulnerabilities.

In Go: The standard library is rich and robust. If you need a 10-line string helper, write it or copy it into your repo rather than importing an external repository.

🛡️ 3. "Errors are values, not exceptions."

In Node.js: throw new Error() bypasses function return signatures, causes invisible execution jumps, and leads to crashes if an unhandled promise rejection slips through.

In Go: Errors are returned as standard secondary values (val, err := fn()). You cannot ignore an error without explicitly writing _. Code execution remains 100% linear.

🔄 4. "Don't communicate by sharing memory; share memory by communicating."

In Node.js / Worker Threads: Shared memory requires SharedArrayBuffer, Atomics, and mutex-like locks that risk deadlocks and race conditions.

In Go: Communicating Sequential Processes (CSP). Instead of locking a shared variable, goroutines send the data packet over a channel. Only the recipient owns the pointer.

⚡ 5. "Make the zero value useful."

In Node.js: Uninitialized properties are undefined. Accessing nested properties crashes the server: TypeError: Cannot read properties of undefined.

In Go: Every type has a deterministic zero value. Standard structs like sync.Mutex, bytes.Buffer, and strings.Builder work immediately upon declaration with no constructor needed.

🧩 6. "Composition over Inheritance" (No classes, no extends)

In Node.js: class Dog extends Animal with super(). Deep inheritance hierarchies suffer from the fragile base class problem.

In Go: Struct embedding. A struct embeds another struct anonymously, promoting its methods and fields. Interfaces are satisfied automatically without implements.

🚫 What Go Deliberately Left Out (and WHY)

Omitted Feature Common in JS / Node.js Why Go Chose NOT to Include It
No Classes or extends class Dog extends Animal Inheritance creates tight coupling and fragile base classes. Go uses struct composition and implicit interfaces.
No Exceptions (throw / catch) try { ... } catch (err) { ... } Exceptions create invisible exit points and hidden control flow. Go treats errors as explicit values that must be handled locally.
No Ternary Operator (? :) const x = cond ? a : b; Ternary expressions frequently get chained into unreadable, ungreppable code. Explicit if / else blocks are clearer.
No Function Overloading / Defaults function find(id = 1, options?) Overloading obscures which function signature is actually invoked. In Go, functions have distinct descriptive names (e.g., NewReader, NewReaderSize).
No Implicit Type Coercion "5" + 2 == "52" and "5" - 2 == 3 Implicit conversions cause notorious JavaScript runtime bugs. In Go, even adding an int32 and an int64 requires an explicit type cast.
No Linter / Formatter Debates Endless ESLint, Prettier, tab vs space wars Go comes with gofmt built-in. There is exactly one standard formatting style enforced automatically by every tool in the Go ecosystem.
🧘 The Zen of Go (Dave Cheney)
  • Each package should have a single purpose: Packages are units of design, not arbitrary folder names.
  • Handle errors gracefully: Never ignore an error. Check them early and return immediately (guard clauses).
  • Avoid package-level state: Keep globals to an absolute minimum to ensure goroutine safety and clean unit testing.
  • Before you solve a problem, make sure you understand it: Don't build speculative abstractions or generic factories until you have three real use cases.
  • Simplicity is complicated: It takes hard work and discipline to keep a codebase simple as it scales.

🎯 Go vs Node.js Backend Interview Mastery

The most frequent and critical interview questions asked by senior engineering teams when evaluating developers transitioning from Node.js/TypeScript to Go.

📊 Architectural Mental Model: Node.js Event Loop vs Go M:N Scheduler
How concurrency actually executes under the hood in both runtimes:
Q1: How does Go's Concurrency model differ fundamentally from Node.js? Most Frequent
Node.js mental model: Single-threaded JavaScript execution engine with an asynchronous event loop. Good for I/O bound tasks; fatal for CPU-heavy tasks without Worker Threads.

Go Architecture: Go uses the M:N Scheduler (M OS threads multiplexed across N Goroutines via P logical processors). Goroutines start with only 2 KB of stack space (compared to 1-2 MB for OS threads or Node Worker threads) and grow dynamically.

Go supports true hardware parallelism across all CPU cores automatically. If a Goroutine blocks on a network syscall or channel, the Go runtime detaches the OS thread and runs another Goroutine instantly (cooperative and preemptive work-stealing).

Interview Pro-Tip: Mention that since Go 1.14, Go has asynchronous preemption using OS signals (SIGURG). Even a tight infinite loop (for {}) without function calls will NOT lock up a CPU core indefinitely.
Q2: What is the "Nil Interface" trap in Go and why does it trip up JavaScript devs? Classic Gotcha
Node.js mental model: In JS, if val === null, then Boolean(val) is always false. In Go, an interface can hold a nil pointer and yet interface != nil evaluates to true!

An interface value in Go is represented under the hood as a two-word tuple: (type, value).

  • An interface is only equal to nil if both its type and its value are nil.
  • If you return a typed pointer that happens to be nil (e.g. var err *MyCustomError = nil) as an error interface, the interface's type is *MyCustomError, so err != nil is TRUE!
func GetUser() error {
    var customErr *NotFoundError = nil
    return customErr // BUG: returns interface(*NotFoundError, nil)
}

func main() {
    if err := GetUser(); err != nil {
        // THIS CODE RUNS even though customErr was nil!
        fmt.Println("Error occurred!")
    }
}
Interview Pro-Tip: Always return explicit nil rather than a typed nil pointer when implementing error returns: return nil.
Q3: What is the difference between an Array and a Slice? How does Capacity growth work? Fundamental
Node.js mental model: JS only has Array, which is an auto-resizing dynamic object on the V8 heap.

In Go:

  • Array ([5]int): Fixed size, part of the type signature. Passed entirely by value (copies all elements when passed to a function).
  • Slice ([]int): A lightweight 24-byte header containing:
    1. Data uintptr (pointer to the underlying array)
    2. Len int (number of accessible elements)
    3. Cap int (total capacity of underlying buffer)

Growth Algorithm: When appending beyond capacity, Go doubles capacity up to 256 elements; beyond 256, it transitions smoothly to growing by ~25% to minimize memory waste.

Q4: How does Go's Garbage Collector differ from Node.js (V8)? Systems Architecture

V8 (Node.js): Uses a Generational Garbage Collector (Scavenger for young generation + Mark-Sweep-Compact for old generation). Optimized for dynamic scripting languages where millions of short-lived objects are born in functions. Can experience stop-the-world pauses under heavy memory churn.

Go Runtime: Uses a Concurrent Tri-Color Mark-and-Sweep Garbage Collector without generational collection or object moving/compaction.

  • Sub-millisecond latency: Go prioritizes predictable low latency over absolute throughput. GC pauses are typically < 0.5 ms.
  • Escape Analysis: Because Go puts the vast majority of local variables and small structs on the stack, they are freed instantly upon function return without GC involvement!
  • Tuning: Controlled primarily by GOGC (default 100% target ratio) and GOMEMLIMIT (Go 1.19+ soft memory ceiling to prevent OOM kills in Docker/Kubernetes).
Q5: What is Escape Analysis and why is it crucial for Go performance? Performance

Escape Analysis is the Go compiler's static analysis step that determines whether a variable can be safely allocated on the fast Stack or must "escape" to the Heap.

  • Stack allocation: Ultra-fast (moving stack pointer), zero GC overhead.
  • Heap allocation: Requires runtime memory allocator and GC tracing.

Common reasons variables escape to heap:

  1. Returning a pointer to a local variable from a function.
  2. Passing values into interface parameters (e.g., fmt.Println(x) takes ...any, forcing x to escape).
  3. Allocating slices with dynamic sizes that cannot be resolved at compile time.
Interview Pro-Tip: You can inspect the compiler's escape analysis decisions in terminal via: go build -gcflags="-m -m".
Q6: How do you identify and prevent Goroutine Leaks in production? Production Reliability

A Goroutine leak occurs when a Goroutine is spawned but remains blocked forever (waiting on a channel that is never written to, or reading from a socket without a timeout). Because Goroutines are never garbage-collected while alive, memory grows monotonically until the pod OOM crashes.

Prevention Strategies:

  • Always pass a cancellable context.Context to long-running or async goroutines.
  • Use buffered channels when you know the number of workers, or use a select with ctx.Done().
  • Monitor total goroutine count in Prometheus using runtime.NumGoroutine().
  • Attach net/http/pprof to inspect live goroutine stack dumps via /debug/pprof/goroutine?debug=1.

⚠️ Known Pitfalls & Footguns (For Node.js Devs)

Common traps where JavaScript intuition leads to silent bugs, race conditions, memory leaks, or unrecoverable panics in Go.

📐 Memory Footprint: JS Object Graph vs Go Contiguous Memory Layout
Why Go structs take 10x less RAM and produce zero garbage collector pointer fragmentation:
🪤 Pitfall 1: Loop Variable Capture in Goroutines

In older Go (pre-1.22) and many concurrent patterns, closures in goroutines capture the reference of the loop variable, not its value at iteration time!

❌ BUGGY: All goroutines print the LAST item
items := []string{"a", "b", "c"} for _, v := range items { go func() { fmt.Println(v) // Captures single pointer! }() } // Outputs: "c", "c", "c"
✅ FIX: Pass variable as explicit argument
items := []string{"a", "b", "c"} for _, v := range items { go func(val string) { fmt.Println(val) // Copied by value! }(v) } // Outputs: "a", "b", "c" (unordered)
🪤 Pitfall 2: Sub-Slicing Retaining Giant Underlying Array

Sub-slicing shares the original array. If you slice 5 bytes from a 50MB file buffer and keep the slice, the entire 50MB array cannot be garbage collected!

❌ BUGGY: Retains 50 MB in RAM forever
func getHeader() []byte { bigFile := read50MBFile() // 50MB buffer return bigFile[:10] // Pointer to 50MB! }
✅ FIX: Copy into newly allocated slice
func getHeader() []byte { bigFile := read50MBFile() header := make([]byte, 10) copy(header, bigFile[:10]) // Independent array! return header // bigFile is garbage collected }
🪤 Pitfall 3: Concurrent Map Mutation Crashes the Process

In JS, single-threading prevents race condition panics. In Go, multiple goroutines writing/reading a map concurrently will throw fatal error: concurrent map read and map write which CANNOT be caught by recover()!

❌ BUGGY: Fatal unrecoverable process crash
m := make(map[string]int) go func() { m["a"] = 1 }() go func() { _ = m["a"] }() // CRASH: fatal error: concurrent map access
✅ FIX: Protect with sync.RWMutex
type SafeMap struct { sync.RWMutex data map[string]int } // Read: mu.RLock(); val := data[k]; mu.RUnlock() // Write: mu.Lock(); data[k] = v; mu.Unlock()
🪤 Pitfall 4: Defer inside Long Loops Leaks File Descriptors

defer does NOT run at the end of a loop iteration; it runs when the surrounding function returns! Putting defer inside a loop of 10,000 files will keep all 10,000 file descriptors open simultaneously.

❌ BUGGY: "too many open files" OS crash
for _, filename := range files { f, _ := os.Open(filename) defer f.Close() // Will NOT close until main() ends! }
✅ FIX: Wrap in helper function or close manually
for _, filename := range files { func(name string) { f, _ := os.Open(name) defer f.Close() // Closes when this anonymous func exits! }(filename) }
🪤 Pitfall 5: Accidental Variable Shadowing with :=

Using := inside an if block creates a new block-scoped variable, shadowing the outer variable and leaving it unchanged.

❌ BUGGY: client remains nil outside if block
var client *HttpClient if env == "prod" { client, err := NewProdClient() // SHADOWS client! } // client is still nil here!
✅ FIX: Declare err separately, use = for client
var client *HttpClient var err error if env == "prod" { client, err = NewProdClient() // Assigns to outer client }
🪤 Pitfall 6: Lowercase (Unexported) Fields Silent JSON Null

In Go, lowercase struct fields are package-private. The encoding/json package is in another package, so it cannot see unexported fields and silently ignores them!

❌ BUGGY: Serializes to empty "{}"
type User struct { name string // Lowercase: Unexported! email string // Lowercase: Unexported! } bytes, _ := json.Marshal(User{"Tom", "t@t.com"}) // Result: "{}"
✅ FIX: Capitalize fields and use struct tags
type User struct { Name string `json:"name"` Email string `json:"email"` } bytes, _ := json.Marshal(User{"Tom", "t@t.com"}) // Result: '{"name":"Tom","email":"t@t.com"}'

🛠️ Go Troubleshooting & Diagnostic Workflows

Step-by-step developer playbook for solving deadlocks, data races, compiler complaints, and production bottlenecks.

🚨 1. Diagnosing: "fatal error: all goroutines are asleep - deadlock!"

This runtime error occurs when every single goroutine is waiting on a channel or lock, and no active goroutine is left to wake them up.

# Step-by-step diagnostic checklist:
1. Did you send to an unbuffered channel without a receiver already waiting?
   ch := make(chan int) // Unbuffered
   ch <- 1 // BLOCKS MAIN GOROUTINE FOREVER -> DEADLOCK!
   Fix: use buffered make(chan int, 1) or send from separate goroutine.

2. Did you forget to close a channel that a "for range" loop is reading from?
   Fix: call close(ch) when writer is finished.

3. Did sync.WaitGroup.Wait() get called without wg.Done() being executed?
   Fix: always write "defer wg.Done()" inside the worker goroutine.
🏎️ 2. Hunting Data Races with the Go Race Detector (-race)

Go includes an integrated ThreadSanitizer race detector. Never deploy multi-goroutine code without running tests under -race.

# Run tests with race detection:
go test -race ./...

# Run local development server with race detector enabled:
go run -race cmd/main.go

# Typical Output Anatomy:
WARNING: DATA RACE

📈 3. Profiling CPU, Memory & Goroutines with net/http/pprof

To diagnose memory leaks or CPU bottlenecks in production, expose the standard pprof HTTP endpoints:

// In your main.go or server setup:
import _ "net/http/pprof"
go func() {
    log.Println(http.ListenAndServe("localhost:6060", nil))
}()

# Inspect live goroutine stack traces in terminal:
curl http://localhost:6060/debug/pprof/goroutine?debug=1

# Capture 30-second CPU profile and analyze with interactive UI:
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/profile?seconds=30
📖 4. Common Go Compiler Errors Quick Reference
Compiler Error Root Cause Instant Fix
"imported and not used" Go treats unused imports as build-breaking errors to prevent binary bloat. Remove the import or prefix with _ "pkg" for side-effects.
cannot use x (type int) as type int64 Go has no implicit type casting between numeric types. Cast explicitly: int64(x).
cannot assign to struct field in map Map elements are not addressable in memory. Store pointer in map (map[string]*User) or reassign the whole struct.
no new variables on left side of := All variables on the left of := already exist in current scope. Use assignment operator = instead of :=.
undefined: MyFunction Function is either not imported, unexported (lowercase), or in a different file in package. Capitalize first letter to export, or run go run . instead of go run main.go.
